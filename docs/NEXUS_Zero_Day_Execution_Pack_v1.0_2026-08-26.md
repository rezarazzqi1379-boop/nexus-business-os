## 3. Product contract to implement now

### Input

- project ID;
- canonical engineering/acceptance master;
- supplier proposal, catalogue, email or quotation;
- user-selected decision objective.

### Processing

1. classify each material statement as FACT, CLAIM, ESTIMATE, ASSUMPTION, HYPOTHESIS or UNKNOWN;
2. map requirements to evidence locators;
3. compare supplier statements against the governing master;
4. produce contradictions, missing evidence and clarification questions;
5. normalize commercial and technical alternatives without inventing equivalence;
6. create a decision packet;
7. enqueue only read-only internal work unless an exact external action is separately approved.

### Output

- requirement/compliance matrix;
- contradiction register;
- missing-evidence register;
- normalized offer comparison;
- recommended next decision with confidence and blockers;
- draft clarification/RFQ response;
- audit record and reproducible test result.

## 5. External patterns transplanted immediately

Research window: 2025-08-26 through 2026-08-26; 40 search results across four workstreams, filtered toward official deployments, practitioner evidence, current research and failure reports.

### Pattern A — system-of-record comparison

Industrial procurement deployments compare incoming email/PDF content against ERP purchase-order truth rather than asking an agent to judge from prose alone.

**NEXUS adoption:** canonical masters become the stable comparison surface; Gmail/quotes remain live evidence; every deviation becomes a typed exception.

### Pattern B — exception-first workflow

High-volume procurement automation creates value by allowing matching cases to flow and routing only price, quantity, date, scope and compliance deviations to humans.

**NEXUS adoption:** Deal Desk UI defaults to the unresolved-exception queue, not an all-document chat interface.

### Pattern C — one vertical, shared foundation

Successful deployments begin with one tightly bounded workflow, validate it on live records and extend the same data/integration foundation.

**NEXUS adoption:** Hydrotester first; Can Forming is the portability proof; KCl is the compliance proof. Do not create three products.

### Pattern D — recommendation feedback

Procurement decision systems improve when users accept/reject suggested opportunities and the reasons are captured.

**NEXUS adoption:** every recommendation receives `accepted`, `corrected`, `rejected` or `deferred`, plus reason and later outcome stage.

### Pattern E — constrained identity and permissions

Agent failures become catastrophic when credentials are over-scoped and destructive actions lack a hard gate.

**NEXUS adoption:** read-only is the default identity; external send, production mutation, merge, deploy and destructive verbs require exact action binding and independent recovery.

## 7. Mandatory acceptance tests

- Hydrotester values remain: OD 89–180 mm, wall 6–20 mm, length 9–12 m, 120 MPa capability, hold 5–10 s, 60 pipes/hour basis.
- Supplier claim never overwrites buyer requirement.
- 70 MPa or incompatible catalogue capability is surfaced as a conflict, not compliance.
- Heat Treatment 40/h uncertainty never enters Hydrotester.
- Can Forming D73/D99 and necking-only/full-line scopes remain distinct.
- KCl preferred 62% grade never silently replaces the minimum acceptance of K2O ≥61%.
- Same deterministic inputs produce the same structured result.
- Unknown evidence never passes a compliance gate.
- Changed recipient/body/attachment/source version invalidates prior send approval.
- Duplicate task or retry cannot create a duplicate consequential action.
- Untrusted document instructions cannot become control-plane commands.
- A failed worker can recover without losing or duplicating intent.
